# Release checklist: 1.91.2

Drafted 2026-11-22 for `v1.91.2`, from `docs/release-checklist.md`; the CI lines are filled on
the release commit. 1.91.2 is one fix, shipped on its own: delegated agents could read and change
the user's own OpenCode store (#1010).

OpenCode 2.x keeps every credential `/connect` and `opencode auth login` store, API keys and
OAuth tokens for every provider, in its database, `~/.local/share/opencode/opencode.db`, and no
longer in `auth.json`. That directory, and OpenCode's state directory beside it, were in every
agent's lane, readable and writable: an agent's shell, or a test it wrote, could read every stored
key, read and change the user's own OpenCode sessions for every project, read OpenCode's
snapshots of other worktrees and its saved tool output, and read the user's own TUI prompts. It
was a bug for every task, GPU tasks included.

Now each task's OpenCode keeps its data and state in a home of its own, `tasks/<task>/opencode/`,
which holds no credentials, and the user's OpenCode data and state directories are hidden from
the agent whole (and a moved `OPENCODE_DB` with them). OpenCode has no switch of its own for
this, so its `XDG_DATA_HOME` and `XDG_STATE_HOME` point at the task's home, in OpenCode's
environment alone; the commands the agent runs get the user's own back through a small shell
shim, so uv, pipx, poetry and pnpm find their data where the user keeps it, and the tests never
see OpenCode's. A formatter or language server that OpenCode starts itself, outside the shell (only
when the user's global OpenCode config turns formatters on), sees the task's home instead. `wb watch`, the reports and the lessons read a task's sessions from its home, and
an older task's from the user's store. When a task closes, OpenCode's snapshots and saved tool and
shell output in its home are removed; its session database stays, with the task. A task's OpenCode no
longer downloads OpenCode's model catalog (`OPENCODE_DISABLE_MODELS_FETCH`), which it would cache, 14 MB,
in every task's database; the catalog built into OpenCode serves.

A local model server behind a key kept with `opencode auth login` works again: workbench read
the key from `auth.json`, which OpenCode 2.x no longer writes, so such a model read "it wants an
API key". It now asks `opencode auth export`, outside the lane, and the task's config layer
carries that key for the task's own provider, and only for a server on this machine (never a
cloud provider's key).

Tasks running when the update lands carry on: their next round starts a fresh session in the
task's own home, given the task, the work so far and the earlier session's last words, since the
agent's OpenCode can no longer reach the session it began in the user's store.

Without Landlock (macOS, older kernels, WSL without it) there is no lane, so the user's
OpenCode store stays readable to an agent's commands there, as `wb doctor` says of the lane; the
task's own home still keeps the agent's OpenCode itself off the user's credentials and sessions.
A key written as a literal `apiKey` in the user's global `opencode.json` stays readable as well:
the agent's OpenCode loads that file itself.
